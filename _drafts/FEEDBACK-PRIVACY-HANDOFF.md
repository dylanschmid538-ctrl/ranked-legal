# Feedback privacy handoff · 2026-10-13

Draft for the in-app feedback release. Do not publish these pages before the app and CloudKit inbox are ready. The public site currently has 34 privacy languages and one English support page.

| Data | Purpose and basis | Stored by / access | Retention |
|---|---|---|---|
| Voluntary message, category, source and consent flag | Answer feedback or support request; handling the user's request | Sent to a Cloudflare Worker, then stored in Apple's CloudKit public database using a private server-to-server key | No fixed automatic deletion period is enforced |
| Optional email **or** phone | Reply outside the app; separate consent | Same CloudKit record; not sent to PostHog or RevenueCat | No fixed automatic deletion period is enforced |
| Network address used for a technical abuse limit | Limit abusive submissions; legitimate interest | Cloudflare Worker rate-limit bindings; no raw address or address hash in the CloudKit feedback record | Provider-level logging and retention are not established |

Source contract: `ranked-messages-recovery/Sources/Features/Support/CustomerFeedbackView.swift` and `CustomerFeedbackService.swift`, inspected on 2026-10-13, plus the Cloudflare Worker -> CloudKit design confirmed for this draft. The app sends a request ID to the Worker; it is not part of the stated CloudKit record. The form has no account, requires no iCloud sign-in, and a reply requires the separate contact toggle. The Worker applies technical abuse limits; its limits are not a single global cap. The exact CloudKit region, Cloudflare/provider-level network logs and their retention were not established here; verify before making a location or raw-IP retention claim. The existing policy's PostHog and RevenueCat sections continue to apply to their separate flows.

**Before release:** Verify the production CloudKit record type's World and Authenticated roles cannot read or write feedback, and that the server-to-server key can access it as intended. The public database is world-readable by default unless its roles are restricted, so do not describe the inbox as private until this is checked. Verify a submission from a device without an iCloud account. Update App Store Connect App Privacy for optional **Contact Info → Email Address / Phone Number**, **User Content → Customer Support** for support messages, and consider **Other User Content** for product ideas; purpose **App Functionality**. Review the network-address handling against Apple's data-type definitions rather than guessing a category. Apple's field guidance: https://developer.apple.com/app-store/app-privacy-details/ . Reconcile the final label against the exact release build, then publish the privacy and support pages together. Keep the email route for access and deletion requests.

Wording decision: no fixed message-retention promise because no scheduled deletion exists. The public pages make no claim about data region, provider logs or exact abuse-limit thresholds. The no-iCloud-sign-in statement describes the app -> Worker -> server-key flow, not a direct CloudKit client write.

References checked on 2026-10-13: [Apple server-to-server CloudKit access](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/CloudKitWebServicesReference/SettingUpWebServices.html), [Apple public-database default access](https://developer.apple.com/documentation/cloudkit/ckdatabase/scope/public), [Cloudflare rate-limit bindings](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/), [Apple App Privacy details](https://developer.apple.com/app-store/app-privacy-details/).
